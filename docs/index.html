Why this project exists

Some problems have too many possible combinations to check one by one. Annealing gives you a practical way to search that space by trying changes, keeping improvements, and sometimes accepting worse moves so the search does not get stuck.

The problem

Routing, scheduling, packing, layout, and assignment problems often involve many variables that pull in different directions. The “best” answer is hard to compute directly.

The approach

Simulated annealing explores neighboring states. It always likes lower-energy states, but early on it can also accept a worse state with some probability.

The expectation

The algorithm is designed to find a good solution, not to prove a perfect global optimum. Tuning temperature, cooling, and state changes matters.

The original inspiration

This repository was inspired by SciShow’s explanation of simulated annealing: The Most Metal Algorithm in Computer Science.

From hot metal to better answers

In metallurgy, annealing heats metal and cools it slowly. Hot atoms move freely; as the metal cools, they settle into lower-energy arrangements.

The algorithm borrows that idea:

  • State — a possible solution.
  • Energy — how bad or costly that solution is.
  • Temperature — how willing the search is to explore.
  • Cooling — the gradual reduction of that willingness over time.

Early randomness helps escape local dead ends. Later stability helps the search settle on a strong answer.

How it works

The simulator repeats a small loop. You supply the domain-specific parts; Annealing handles the accept/reject and cooling process.

1

Start

Begin with an initial state and an initial temperature.

2

Measure

Your energy_calculator scores the current state. Lower is better.

3

Change

Your state_change proposes a nearby state to try next.

4

Decide

Better states are accepted. Worse states may still be accepted while hot.

5

Cool

Temperature drops until the termination condition says the run is done.

Important: at temperature zero, the annealer accepts only strictly lower-energy states. Equal or higher energy is not accepted at that point.

Quick start

The classic example is the traveling salesperson problem: visit every location once while keeping the total route short. The example below uses a small custom temperature and cooling rate so it runs quickly.

Ruby

require "annealing"

Location = Struct.new(:x, :y) do
  def distance(other)
    dx = (x - other.x).abs
    dy = (y - other.y).abs
    Math.sqrt(dx**2 + dy**2)
  end
end

locations = [
  Location.new(60, 200),
  Location.new(180, 200),
  Location.new(40, 120),
  Location.new(100, 120),
  Location.new(20, 40)
].shuffle

energy_calculator = lambda do |step|
  step.state.each_cons(2).sum { |a, b| a.distance(b) }
end

state_change = lambda do |step|
  swapped = step.state.dup
  i, j = Array.new(2) { rand(swapped.size) }
  swapped[i], swapped[j] = swapped[j], swapped[i]
  swapped
end

route = Annealing.simulate(
  locations,
  energy_calculator: energy_calculator,
  state_change: state_change,
  temperature: 5_000,
  cooling_rate: 0.5
)

p route.map { |loc| [loc.x, loc.y] }
Why the custom temperature/cooling rate? The default configuration (temperature: 10_000, cooling_rate: 0.0003) considers about 33 million proposed states. That is useful for thorough searches, but too slow for a first experiment.

Configuration

You can configure Annealing globally, on a simulator instance, or for a single run. Later scopes override earlier ones: global < simulator instance < just in time.

Option Default Purpose
cool_down Coolers.linear Calculates the next temperature from an Annealing::Step.
cooling_rate 0.0003 Amount used by the default linear cooler; available to custom coolers as step.cooling_rate.
energy_calculator None, required Scores a state. Lower energy means a better solution. Use step.state, not step.energy.
state_change None, required Returns the next candidate state based on step.state.
temperature 10_000.0 Starting temperature. Higher values allow more exploration.
termination_condition Terminators.temp_is_zero? Returns true when the simulation should stop.
return_best false Return the best state seen during the run instead of the final state.

The Step object

Every custom function receives one Annealing::Step with read-only data:

  • state — current state.
  • energy — current energy.
  • temperature — current temperature.
  • cooling_rate — configured cooling rate.
  • steps — completed step count.

Built-in helpers

Coolers

  • Coolers.linear
  • Coolers.exponential
  • Coolers.geometric(ratio)

Terminators

  • Terminators.energy_or_temp_is_zero?

Learn more

A few practical notes for getting useful results from the gem.

Good use cases

Use annealing when you can score a candidate solution and generate nearby alternatives, but checking every possibility is impractical.

Tuning tips

Start with a small problem. If results are unstable, raise temperature or lower cooling rate. If runs are too slow, reduce steps or add a custom termination condition.

Common pitfalls

Do not call step.energy inside energy_calculator. Keep state changes small. Remember that Annealing.simulate returns the final state unless you configure return_best.
